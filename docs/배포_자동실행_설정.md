# PREVI 운영 서버와 자동 실행 설정

2026-10-29 · BE A · 파일 준비와 실제 서버 등록을 구분한다.

## 공통 확인

한 운영 컴퓨터에서만 자동 작업을 켠다. 학교 서버와 GPU PC에서 동시에 켜지 않는다. DB는 기존 Supabase를 사용하므로 마이그레이션·문서 적재·임베딩을 다시 실행하지 않는다.

운영 코드는 `통합본`에 필요한 PR이 합쳐진 버전을 사용한다. 커밋 SHA로 체크아웃한 상태에서는 바로 `git pull`하지 않고 먼저 `git switch 통합본`으로 돌아간다.

서버 루트의 `.env`, 가상 환경, Ollama 모델, `/health`, 실제 로그인·챗봇 응답을 먼저 확인한다. `/health` 성공만으로 AI 모델과 실제 푸시가 정상이라는 뜻은 아니다. 비밀 키는 서비스 파일·명령줄·깃에 넣지 않는다.

## Linux 학교 서버: 사용자 systemd

전제: systemd 사용자 세션 사용 가능, `/usr/bin/flock` 존재, 서버에 Python 가상 환경과 Ollama가 준비됨. 아래 절차는 Windows에서 실행하지 않는다. 프로젝트 경로는 영문·숫자·밑줄·점·하이픈·슬래시만 지원한다.

### 1. 파일 생성과 점검

학교 서버의 저장소 루트에서 실행한다. 기본 명령은 출력만 하며 `--output-dir`을 줘도 서비스 등록은 하지 않는다. 비어 있지 않은 출력 폴더는 덮어쓰지 않는다.

```bash
.venv/bin/python -m server.scripts.prepare_linux_services
.venv/bin/python -m server.scripts.prepare_linux_services --output-dir "$HOME/previ-units"
command -v flock
systemctl --user status
systemd-analyze --user verify "$HOME/previ-units/"*.service "$HOME/previ-units/"*.timer
systemd-analyze calendar '*-*-* 09:00:00 Asia/Seoul'
systemd-analyze calendar '*-*-* *:0/5:00 Asia/Seoul'
```

학교 서버 경로가 기본 지원 범위 밖이면 시스템에 맞게 파일을 별도 검토하고 경로를 조정한다. 이 도구는 Ollama 설치나 시스템 전역 서비스 변경을 하지 않는다.

### 2. 검토한 파일 등록

기존 `previ-*` 사용자 서비스가 있으면 먼저 내용을 확인·백업하고 갱신한다. 다음 명령은 실제 운영 등록 단계이며 학교 서버 사용 권한 범위에서 실행한다.

```bash
mkdir -p "$HOME/.config/systemd/user"
cp -i "$HOME/previ-units/"*.service "$HOME/previ-units/"*.timer "$HOME/.config/systemd/user/"
systemctl --user daemon-reload
systemctl --user enable --now previ-api.service
curl --fail http://127.0.0.1:8000/health
systemctl --user enable --now previ-collect.timer previ-daily.timer previ-reminders.timer
systemctl --user list-timers 'previ-*'
```

- 공지 수집: 한국 시간 09:00~18:00 매 정각, 하루 10회 (2026-10-31 변경). 기존 설치는 아래의 수집 타이머만 갱신해야 적용된다.
- 아침 점검: 한국 시간 8:50.
- 알림: 5분 간격. PR #9가 함께 반영돼야 Expo 결과 확인도 포함된다.
- 자동 작업끼리는 공통 잠금을 사용한다. 다른 작업 실행 중이면 중복 실행을 건너뛰고 다음 예약 시각에 시도한다.
- 타이머는 `Persistent=false`로 두어 재가동 시 놓친 무거운 작업을 즉시 실행하지 않는다. 장시간 중단했다면 시연 시간을 피해서 수집·점검을 수동 보충한다.
- API는 터널·SSH 연결을 위해 `127.0.0.1:8000`에만 연다. 학내 IP로 직접 접속해야 하면 노출 범위를 확인하고 별도로 변경한다.
- 기본 사용자 서비스는 로그아웃·재부팅 후 지속 실행을 보장하지 않는다. `loginctl show-user "$USER" -p Linger`로 확인하고, 필요하면 관리자에게 사용자 서비스 유지(linger) 또는 시스템 서비스 등록을 요청한다. 이 도구가 관리자 설정을 바꾸지는 않는다.

#### 기존 서버의 API 접속 기록을 30일 보관으로 변경

처리방침 3조의 30일을 지키기 위한 설정이다. 공용 journald 설정은 건드리지 않고, API 로그만 `logs/api.log`로 빼서 날짜별로 나누고 30일이 지난 파일을 지운다. 서비스가 사용자 systemd가 아니거나 경로가 다르면 맞게 바꾼다. API를 재시작한다.

```bash
cd ~/front-back-kick &&
git switch 통합본 && git pull &&
.venv/bin/python -m pip install -r server/requirements.txt &&
mkdir -p ~/.config/systemd/user/previ-api.service.d &&
cat > ~/.config/systemd/user/previ-api.service.d/log-30-days.conf <<'EOF'
[Service]
ExecStartPre=/usr/bin/mkdir -p %h/front-back-kick/logs
ExecStart=
ExecStart=%h/front-back-kick/.venv/bin/python -m uvicorn server.main:app --host 127.0.0.1 --port 8000 --log-config server/log_config.json
EOF
systemctl --user daemon-reload &&
systemctl --user restart previ-api.service &&
curl --fail http://127.0.0.1:8000/health &&
ls -l logs/api.log &&
git rev-parse --short HEAD
```

새 로그부터 적용된다. 전환 전에 journald에 남은 API 기록은 지워지지 않는다. 아래로 가장 오래된 날짜를 확인하고, 그 날짜부터 30일이 되기 전에 서버 관리자에게 삭제를 요청한다.

```bash
journalctl --user -u previ-api.service -o short-iso --no-pager | head -2
```

#### 기존 서버의 수집 시각만 변경

저장소를 pull한 것만으로 기존 systemd 설정이 바뀌지는 않는다. 아래는 기존 예약을 초기화하고 새 예약 10개를 추가하는 drop-in만 만든다. API·Ollama·ngrok·웹 서비스와 일일 점검·리마인더 설정은 건드리지 않는다. 수집 작업도 즉시 실행하지 않는다.

```bash
cd ~/front-back-kick &&
if .venv/bin/python - <<'PY'
from pathlib import Path
from datetime import datetime
from server.scripts.prepare_linux_services import render_units

folder = Path.home() / '.config/systemd/user/previ-collect.timer.d'
folder.mkdir(parents=True, exist_ok=True)
target = folder / '10-hourly.conf'
if target.exists():
    target.with_name('10-hourly.conf.' + datetime.now().strftime('%Y%m%d%H%M%S%f') + '.bak').write_bytes(target.read_bytes())
unit = render_units(Path.cwd().as_posix())['previ-collect.timer']
times = [line for line in unit.splitlines() if line.startswith('OnCalendar=')]
assert len(times) == 10
target.write_text('[Timer]\nOnCalendar=\n' + '\n'.join(times) + '\n', encoding='utf-8')
print('수집 예약 10개 저장 완료. systemd 적용 필요.')
PY
then
systemctl --user daemon-reload &&
systemctl --user restart previ-collect.timer &&
systemctl --user show previ-collect.timer -p TimersCalendar &&
systemctl --user list-timers 'previ-*' --all --no-pager
fi
```

타이머가 실행 중인지와 유효 예약 10개를 확인한다. 기존에 다른 이름의 수집 타이머 drop-in을 직접 만든 서버에서는 이후 파일이 예약을 추가·덮어쓸 수 있으니 `systemctl --user cat previ-collect.timer`도 대조한다.

처리량은 기존 설정을 유지한다. 매 실행은 학사·장학 게시판 각 3페이지, 발견 글 최대 150건을 살피되 기존 게시글 ID는 건너뛴다. 신규/실패 공지 AI 정리는 회당 최대 20건이며 신규 대기 공지를 우선한다. 따라서 매회 새 공지 150건을 AI 처리하는 것은 아니다. 실패한 이미지·첨부 공지는 새 실행마다 다시 시도될 수 있고, 주기 변경이 OCR·HWP 추출을 추가하지는 않는다. 한 시간 넘게 작업이 이어지거나 다른 자동 작업이 잠금을 잡은 경우 해당 실행은 건너뛸 수 있다.

### 3. 상태 확인과 중지

```bash
systemctl --user status previ-api.service
journalctl --user -u previ-api.service -n 50 --no-pager
journalctl --user -u previ-reminders.service -n 50 --no-pager
systemctl --user disable --now previ-collect.timer previ-daily.timer previ-reminders.timer
systemctl --user disable --now previ-api.service
```

중지 명령은 해당 PREVI 서비스만 대상으로 한다. 타이머 중지는 이미 실행 중인 작업을 종료하지 않으므로 서버 이동 전에 `systemctl --user status previ-collect.service previ-daily.service previ-reminders.service`도 확인한다.

## Windows GPU PC

저장소 루트 PowerShell에서 실행한다. 첫 명령은 미리보기, 두 번째가 실제 등록이다.

```powershell
& .\server\jobs\Register-AssistantTasks.ps1
& .\server\jobs\Register-AssistantTasks.ps1 -Register
Get-ScheduledTask -TaskName 'SKU-AI-*' | Select-Object TaskName, State
```

- 한국 시간대여야 한다. 기본 Python은 저장소 `.venv\Scripts\python.exe`다.
- 이번 수정으로 PowerShell 7에서 등록기를 실행해도 실제 Windows PowerShell 경로를 찾도록 했다.
- 현재 등록 방식은 등록한 사용자가 로그인한 상태에서 실행된다. 로그아웃 상태에서의 실행·재부팅 후 API 재시작은 별도 설정이 필요하다.
- 실행 로그는 저장소의 `logs/`에 남는다. PC 절전 상태에서는 예약 실행을 보장하지 않는다.
- 이미 다른 Python으로 API가 실행 중이면 같은 8000 포트에 두 번째 서버를 켜지 않는다.

## 고정 주소와 실제 확인: 아직 필요한 결정

### 기존 임시 API 터널을 ngrok 고정 API로 전환

학교 서버에서 `previ-ngrok.service`의 고정 주소 연결을 먼저 확인한다. 학생 앱과 관리자 웹의 API 클라이언트는 ngrok 주소일 때만 `ngrok-skip-browser-warning` 헤더를 보내 무료 안내 HTML 대신 API 응답을 요청한다.

이미 `.local/previ-tools/previ-share.sh`로 API·웹 임시 터널을 관리하는 호스트는 다음 도구로 API 터널 생성 부분만 제거하고 고정 주소를 유지할 수 있다. 웹 터널과 재빌드는 유지한다. 기본 실행은 미리보기이고, `--apply`는 기존 스크립트 백업·Bash 문법 검사 후 사용자 서비스 의존성을 기록한다. 실제 재시작은 별도로 한다.

```bash
.venv/bin/python -m server.scripts.use_fixed_api --api-url https://<고정-API-호스트>
.venv/bin/python -m server.scripts.use_fixed_api --api-url https://<고정-API-호스트> --apply
systemctl --user daemon-reload
systemctl --user restart previ-share.service
```

공유 스크립트의 형식이 예상과 다르면 변경을 중단한다. 이 도구는 ngrok 설치·토큰 저장을 하지 않으며, 토큰은 저장소 밖의 사용자 전용 설정 파일에 둔다. 전환 후 `app/.env`의 API 주소, 공개 `/health`, 학생 웹 로그인·채팅, 서비스 재시작 후에도 같은 API가 유지되는지 확인한다. 웹 공유 주소 자체는 임시 터널을 쓰면 바뀔 수 있다.

운영 장소, 학교 SSH 주소·계정, GPU 여유 메모리, 설치 권한, 고정 주소에 사용할 도메인·터널 접근 권한은 아직 이 작업에서 확인하지 못했다. 실제 접속 정보나 권한 없이 학교 서버에 등록했다고 간주하지 않는다.

API의 임시 터널 주소가 바뀌면 앱의 API 주소를 수정하고 웹을 다시 빌드한다. 고정 주소를 만들려면 사용할 도메인과 Cloudflare 계정을 결정해야 한다. Ollama의 11434 포트는 공개하지 않는다.

실제 폰 푸시는 FE 개발 빌드에서 토큰 등록을 확인한 후 운영 서버의 `PUSH_ENABLED=true`로 함께 검증한다. 이번 파일 준비 과정에서는 키 설정·서비스 등록·실제 발송을 실행하지 않았다.
